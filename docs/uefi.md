# Загрузка MyOS через UEFI x64

`make usb-image` создаёт единый образ `build/myos-usb.img` с загрузчиками
BIOS/CSM и UEFI x64. Для UEFI CSM не нужен. Установщик `setup` переносит оба
загрузчика на выбранный SATA/AHCI-диск или NVMe namespace.

## Настройки и ограничения

- Нужна **64-битная x86 UEFI**; IA32 UEFI и ARM не поддерживаются.
- **Secure Boot выключить**: загрузчик не подписан.
- Ядро остаётся 32-битным. Framebuffer GOP и PCI MMIO-регистры используемых
  NVMe/xHCI-контроллеров должны находиться ниже 4 ГиБ. Если прошивка размещает
  их выше, отключить Above 4G Decoding; для GPU может понадобиться отключить
  Resizable BAR. Диагностика NVMe выводит причину отказа в журнал ядра.
- Поддерживается линейный GOP 32 bpp с BGRX/RGBX-порядком или эквивалентными масками,
  до 5120 пикселей по каждой координате, framebuffer до 64 МиБ. PixelBltOnly и иной
  формат пикселей отклоняются до запуска ядра.
- Разметка создаётся как MBR: MyFS в первом разделе, FAT32 ESP во втором
  (тип `0xEF`). Такая ESP предусмотрена UEFI; GPT и конвертация существующей
  GPT-разметки в этой версии не реализованы. Существующая GPT отклоняется
  установщиком до стирания.
- Для NVMe сохраняются ограничения драйвера: обычный NVM Command Set,
  логический сектор 512 байт без metadata/protection information, без RAID/VMD.

Поддержка ESP в MBR описана в [UEFI, раздел 5](https://uefi.org/specs/UEFI/2.10/05_GUID_Partition_Table_Format.html).

## Как загрузиться

Записать новый `myos-usb.img` на флешку обычным способом и выбрать её UEFI-пункт
в меню прошивки. После установки на диск извлечь флешку и выбрать установленный
диск как UEFI-устройство. Загрузочный файл — `\EFI\BOOT\BOOTX64.EFI`.
Если прошивка не добавляет такой диск автоматически, выбрать этот файл через
Boot From File / Add Boot Option в её настройках. Установщик не меняет BootOrder
и не записывает переменные загрузки NVRAM.

`USB_VIDEO=1280x720 make usb-image` задаёт желаемый режим также для UEFI.
В режиме `auto` выбирается родной размер монитора из EDID или наибольший
подходящий доступный режим. Ограничения RAM, fallback и безопасное меню описаны
в [display-modes.md](display-modes.md). После ExitBootServices
разрешение GOP фиксировано; BIOS-интерпретатор режимов для UEFI не включается.

При UEFI в журнале будут строки `Boot: UEFI x64, firmware services exited`
и `Graphics: UEFI GOP framebuffer` (для соответствующего NVIDIA-выхода —
`NVIDIA UEFI GOP`). Installed root монтируется напрямую через AHCI/NVMe,
а Live читает начальный MyFS-образ в RAM и использует USB persistence, если
доступен xHCI BOT. Путь boot disk проверяется по UEFI Device Path и MBR ID.

## Что делает загрузчик

1. Загружает конфигурацию, ядро и bitmap-шрифт с FAT32 ESP. Проверяет размер
   и CRC32 ядра, геометрию MyFS и идентичность физического загрузочного носителя.
2. Выбирает подходящий GOP-режим. Для Live выделяет непрерывную RAM ниже 1 ГиБ
   через AllocatePages и читает MyFS через EFI Block I/O. Фиксированного адреса
   RAM-корня, используемого BIOS-загрузчиком, в UEFI не требуется.
3. Получает ACPI RSDP из configuration table, переводит карту памяти UEFI
   в поддерживаемый ядром формат, резервирует собственный arena/стек/шрифт.
   Низкая страница AP trampoline резервируется отдельно; если она недоступна,
   ядро остаётся на одном CPU и не перезаписывает память прошивки.
4. Завершает Boot Services с актуальным MapKey, повторяя GetMemoryMap при
   смене ключа. Затем через собственные GDT и identity page tables выходит
   из long mode и передаёт управление 32-битному ядру. Вызовов BIOS или UEFI
   Runtime Services после этого нет. При раннем отказе выделенные страницы
   освобождаются перед возвратом в Boot Manager.

Boot-info v4 содержит адрес карты памяти, RSDP и выделенной arena. PMM исключает
ядро, RAM-корень и arena из свободных страниц. Контракт BIOS v1–v3 сохранён.
Шрифт `FONT.BIN` растеризован из Ubuntu Mono; его лицензия лежит рядом в `FONT.LIC`.

## Live-образ с Google Chrome x86-64

Для сборки нужен Linux x86-64 с GNU Make, GCC, NASM, GNU-EFI, Python с Pillow,
библиотеками Wayland и xkbcommon для композитора, wayland-scanner,
wayland-protocols и штатными библиотеками времени выполнения Chrome,
включая NSS. Для запуска нужны QEMU с GTK и e1000, а также OVMF.

Укажите путь к бинарнику из официального дистрибутива Google Chrome для Linux.
Например, можно распаковать официальный deb-файл в отдельный каталог и
передать путь к `opt/google/chrome/chrome`. Бинарник и ресурсы Chrome
входят в собранный образ.

```sh
make kernel-x64-chrome-image CHROME_BIN=/path/to/chrome/opt/google/chrome/chrome
make kernel-x64-chrome-run CHROME_BIN=/path/to/chrome/opt/google/chrome/chrome
```

Результат сборки — `build/x86_64/myos-chrome.img`. Цель запуска загружает
его в QEMU и открывает Chrome на Wayland. Начальную страницу можно выбрать
через `CHROME_URL`, например `CHROME_URL=about:blank`. Для пользовательской
прошивки задайте переменные окружения `OVMF_CODE` и `OVMF_VARS` из одной
поставки OVMF.

Chrome использует программный вывод и `--jitless`. По умолчанию профиль
хранится в `/tmp` гостя до завершения сеанса. Постоянный профиль можно
запустить с отдельным образом MyFS.

```sh
make kernel-x64-chrome-run CHROME_BIN=/path/to/chrome/opt/google/chrome/chrome \
  CHROME_PROFILE=/path/to/myos-chrome-profile.img
```

При первом запуске команда создаст разреженный том на 1 ГиБ. Чтобы открыть
тот же профиль, укажите тот же `CHROME_PROFILE` при следующем запуске.
Профиль находится на отдельном NVMe-диске QEMU. Завершите работу Chrome через
его меню или закройте все окна браузера перед закрытием QEMU.

`make kernel-x64-chrome-smoke CHROME_BIN=...` проверяет в QEMU загрузку
HTTPS-страницы с доверенным тестовым CA и отказ для того же сертификата
без доверия к CA. Для теста нужны OpenSSL и `certutil` из NSS.
`make kernel-x64-chrome-profile-smoke CHROME_BIN=...` проверяет штатный
лаунчер, завершение Chrome и восстановление данных сайта после холодной
загрузки с тем же диском профиля.

## Сборка и проверки

Для проверки перехода в x86-64 используется отдельный тестовый образ.
В `BOOT.CFG` версии 2 значение `kernel_abi=1` выбирает x86-64. Смещения
прежних полей сохраняются. Штатные USB-образы и установщик используют
`BOOT.CFG` версии 1 для i386.

При x86-64 загрузчик оставляет процессор в long mode, устанавливает собственное
тождественное отображение первых 4 ГиБ и передаёт управление адресу
`0x100000`. `RDI` содержит указатель на boot-info v5, `ESI` содержит
`0x55454649`, а стек выровнен по SysV AMD64 на входе в функцию.
Прерывания отключены, IDT пуста. Память от конца файла до `kernel_end`
обнулена. Следующую IDT должен установить сам загруженный код.

В Ubuntu/WSL кроме обычных зависимостей нужны `gnu-efi` и `python3-pil`.
Для тестов также нужны `ovmf`, `qemu-system-x86`, `dosfstools`, `mtools`.
Для EFI-приложения и цели `kernel-x64` нужны GCC с поддержкой x86-64,
GNU ld и objcopy. EFI-приложение получается в `build/uefi/BOOTX64.EFI`.
Штатное ядро MyOS по этим целям загрузочных образов собирается для i386.

- `make uefi-loader` — только EFI-приложение.
- `make uefi-x64-smoke` — переход после `ExitBootServices` в тестовый код
  x86-64 под OVMF, проверка режима CPU, стека, таблиц страниц и boot-info.
- `make kernel-x64` — отдельное freestanding-ядро в `build/x86_64/kernel.bin`.
  После передачи управления ядро проверяет границы и записи карты памяти UEFI,
  выводит диагностику через COM1 и устанавливает IDT для исключений CPU.
  Обработчик печатает номер, код ошибки и RIP, затем останавливает процессор.
  Используемые стек, GDT и таблицы страниц остаются в арене UEFI-загрузчика.
- `make kernel-x64-smoke` — обычная загрузка этого ядра и отдельные образы
  для проверки исключений #UD и #GP с аппаратным кодом ошибки под OVMF.
- `make kernel-x64-pmm-smoke` — выделение и возврат физических страниц под
  OVMF, включая загрузку с Live RAM-корнем. Аллокатор использует доступную
  память ниже 1 ГиБ из карты UEFI, сохраняет образ ядра, загрузочную арену,
  RAM-корень и область видеобуфера, если она пересекается с этим диапазоном.
- `make kernel-x64-paging-smoke` — переключение на собственный CR3, доступ
  к выделенной памяти и проверки #PF с точными CR2 и кодами ошибок. Ядро
  оставляет низкие отображения для своего образа и загрузочной арены.
  Доступная RAM отображается от `0xffff800000000000` с правами супервизора.
  NX запрещает исполнение из прямого отображения, а WP защищает код и rodata
  от записи через низкие и высокие адреса. Для этого режима нужен CPU с NX.
- `make kernel-x64-gop-smoke` — вывод кадра через GOP с проверкой цветов
  и геометрии по снимку QEMU. Ядро отображает видеобуфер отдельно от RAM
  с типом памяти UC, только для супервизора и без права исполнения.
  Тест выводит кадр после переключений в таблицы страниц `fork` и `exec`,
  затем проверяет аппаратный отказ при чтении из ring 3.
  В Linux ABI x86-64 процесс может выводить кадры через `/dev/fb0`.
  `FBIOGET_VSCREENINFO` и `FBIOGET_FSCREENINFO` возвращают фиксированную
  геометрию GOP, порядок цветовых каналов и шаг строки. `read`, `write`,
  `pread64` и `pwrite64` работают с байтами этого формата в пределах
  видеобуфера. Аппаратный адрес скрыт, `mmap` возвращает `ENODEV`.
  Тест Linux ABI выводит цвета из ring 3 и сверяет снимок QEMU.
- `make kernel-x64-wayland-smoke` — композитор в Linux ABI x86-64
  принимает окно `xdg-shell` и выводит `wl_shm`-буфер через `/dev/fb0`.
  Отдельный клиент проверяет подтверждение кадра, освобождение буфера
  и повторный показ окна. Тест сверяет пиксели клиента на снимке QEMU.
  Для сборки в Linux нужны заголовки и библиотеки `wayland-client` и
  `wayland-server`, `wayland-scanner`, протоколы `wayland-protocols`, `libxkbcommon`,
  данные XKB и `pkg-config`.
  Композитор находится в `build/x86_64/wayland/wayland-compositor` и
  принимает путь Unix-сокета первым аргументом. Карта клавиатуры в формате
  XKB v1 берётся из `/myos/keyboard.xkb` или из неизменяемого на время запуска
  файла, переданного вторым аргументом. Сборка генерирует `keyboard.xkb` с раскладкой US.
  Один `wl_seat` передаёт клавиши и модификаторы клиенту видимой поверхности
  `xdg_toplevel`, а движение, кнопки и колесо — клиенту под указателем.
  Композитор выводит курсор поверх кадра и восстанавливает фон при перемещении.
  Тест через QMP проверяет клавиатуру, указатель, фокус и пиксели курсора.
  Поддержка окон композитора пока ограничена ролью `xdg_toplevel`.
- `make kernel-x64-ethernet-smoke` — драйвер эмулируемого Intel 82540EM (`8086:100e`)
  опрашивает RX и TX без аппаратных прерываний. Ядро использует назначенный UEFI
  PCI BAR с отображением UC и передаёт устройству физические адреса DMA.
  Стенд QEMU сверяет ARP-ответы шлюза `10.0.2.2` в госте и в PCAP.
  Тест проходит оба кольца по кругу, отключает линк и проверяет обмен после
  его восстановления. Linux-образ инициализирует этот адаптер при наличии.
- `make kernel-x64-ipv4-smoke` — IPv4 с одним интерфейсом. Ядро выбирает прямой
  маршрут или шлюз, запрашивает MAC через ARP и проверяет длину, адрес назначения
  и контрольную сумму входящего заголовка. Стенд задаёт адрес и маршрут явно,
  подтверждает ICMP-ответ шлюза QEMU и сверяет прямой и внешний маршруты по PCAP.
- `make kernel-x64-dhcp-smoke` — обычный Linux-образ x86-64 запускает
  программу в ring 3 с отключённым линком. После включения e1000 клиент DHCPv4
  получает адрес, маску, шлюз, DNS и срок аренды. Тест сверяет обмен по PCAP
  и проверяет ARP и ICMP с назначенного адреса. DHCP обслуживается планировщиком,
  продлевает аренду на T1/T2 и сбрасывает конфигурацию при потере линка.
- `make kernel-x64-udp-smoke` — обычный Linux ELF использует IPv4 UDP через
  `AF_INET/SOCK_DGRAM`. Сокеты сохраняют границы датаграмм, поддерживают
  привязку и выбор удалённого адреса, loopback, `poll` и `epoll`.
  QEMU сверяет обмен с тестовым соседом по PCAP и проверяет адрес отправителя.
- `make kernel-x64-udp-recverr-smoke` — QEMU возвращает ICMP-ошибку на исходящую
  UDP-датаграмму. Linux ELF проверяет `POLLERR`, `SO_ERROR`, адрес отправителя
  и процитированные данные в `recvmsg(MSG_ERRQUEUE)` на сокете с `IP_RECVERR`.
- `make kernel-x64-tcp-smoke` — Linux ELF открывает исходящее соединение
  `AF_INET/SOCK_STREAM`, ждёт завершения через `epoll`, читает `SO_ERROR`
  и обменивается потоком с TCP-сервером через QEMU. PCAP сверяет рукопожатие,
  данные и FIN. Блокирующий `connect` к закрытому порту возвращает
  `ECONNREFUSED`. Хостовый тест проверяет RTO, повтор сегмента и обработку RST.
- `make kernel-x64-dns-smoke` — динамически связанный Linux ELF разрешает
  имя через `getaddrinfo`. QEMU сверяет DNS-запросы к серверу из аренды DHCP.
  Linux ABI публикует этот сервер в `/etc/resolv.conf`, если Live-образ не
  содержит собственной настройки. Открытый файл сохраняет своё содержимое
  при смене или потере аренды.
- `make kernel-x64-shm-smoke` — Linux ELF проверяет RAM-каталог `/dev/shm`
  с правами `01777`, общую страницу после `fork` и доступ к старому
  отображению после удаления имени. Новый файл с тем же именем получает
  отдельное хранилище.
- `make kernel-x64-seccomp-smoke` — Linux ELF проверяет фильтрацию системных
  вызовов, отказ в установке некорректной программы без замены старой,
  наследование при `fork` и `execve` и согласование цепочек при `TSYNC`.
  Тест также проверяет контекст `SIGSYS` при `SECCOMP_RET_TRAP` и возврат
  из обработчика. Действия с отсутствующим обработчиком остаются запрещёнными.
- `make kernel-x64-ring3-smoke` — переход через `IRETQ` к тестовому коду
  пользователя и вход обработчика на отдельный стек `TSS.RSP0`. Пользовательский
  код отображён RX, его прямой псевдоним RO/NX, стек RW/NX. Тесты сверяют CPL,
  пользовательский RSP, запрет чтения ядра, записи в код и исполнения стека.
- `make kernel-x64-linux-smoke` — отдельный тестовый образ x86-64 запускает
  статический Linux ELF64 с начальными `argc`, `argv`, `envp` и `auxv`.
  Тест проверяет `write` в stdout/stderr и `exit` через `SYSCALL`,
  ограничения отображений ELF, ошибки доступа к памяти и неверный стек
  возврата. Та же цель проверяет запуск PIE с `PT_INTERP`. Тестовый
  интерпретатор проверяет `AT_BASE`, `AT_PHDR` и `AT_ENTRY`, затем передаёт
  управление основному ELF. Образы для теста берутся из Live RAM-диска,
  адреса загрузки фиксированы. Для этого этапа нужен хост Linux x86-64 с GNU ld.
  Интерпретатор и открываемые через Linux ABI файлы читаются из одного
  набора в Live RAM-диске. В наборе обычные файлы с точными путями и текущим
  каталогом `/`. `AT_EMPTY_PATH` поддерживает открытый дескриптор файла.
  Проверка сравнивает `openat`, `read`, `pread64`,
  `newfstatat` и `close` с Linux, включая границы страниц и ошибки указателей.
  Тестовый Linux ABI поддерживает приватные файловые и анонимные `mmap`,
  а для неизменяемых файлов Live-образа также `MAP_SHARED`. Попытка включить
  запись через `mmap` или `mprotect` в такое общее отображение возвращает
  `EACCES`, в том числе после закрытия дескриптора.
  `memfd_create` создаёт анонимный файл в памяти размером до 256 МиБ.
  `ftruncate` задаёт размер, `fcntl` позволяет запретить изменение размера и
  добавление новых seals. Через `openat` по `/proc/self/fd/N` можно открыть
  отдельный дескриптор только на чтение. Общие отображения видят записи
  друг друга и сохраняют страницы после закрытия всех дескрипторов.
  Общие страницы `memfd` всегда NX. Изменение размера при живом общем
  отображении возвращает `EBUSY`, если его раньше не запретили seals.
  Общее отображение целых страниц за EOF доступно с `F_SEAL_GROW` и даёт
  диагностический #PF при обращении.
  `socket(AF_UNIX, SOCK_STREAM, 0)` создаёт потоковый сокет без соединения.
  `fcntl` меняет неблокирующий режим открытого сокета и `FD_CLOEXEC`
  отдельного дескриптора. `bind` создаёт имя в доступной для записи части VFS,
  `listen` открывает очередь, `connect` ставит соединение в неё, а `accept`
  и `accept4` выдают второй дескриптор. Удаление имени сохраняет открытые
  соединения. Поток передаёт байты по порядку и сохраняет непрочитанный хвост.
  Блокирующие операции ждут готовности в планировщике.
  `socketpair(AF_UNIX, SOCK_STREAM)` создаёт два уже соединённых
  потоковых сокета без имени. Пара `SOCK_SEQPACKET` сохраняет границы
  сообщений при `read`/`write` и `recvmsg`/`sendmsg`.
  `SCM_RIGHTS` передаёт ссылки на открытые файлы через оба типа сокетов.
  Получатель получает свои номера дескрипторов и может задать
  `MSG_CMSG_CLOEXEC`. Усечение управляющих данных помечается `MSG_CTRUNC`.
  Планировщик освобождает циклы ссылок в очередях, недостижимых извне.
  `sendto` передаёт данные через соединённые Unix-сокеты. `MSG_DONTWAIT`
  отключает ожидание только для этой отправки. Отправка с `MSG_NOSIGNAL`
  возвращает `EPIPE` при закрытом направлении записи. Доставка `SIGPIPE`
  в Linux ABI пока не реализована.
  `SO_PEERCRED` возвращает PID, UID и GID другой стороны Unix-соединения
  в пространствах имён вызывающего процесса. Для `socketpair` ядро
  сохраняет данные создателя. При `connect` оно сохраняет данные клиента
  и того, кто выполнил `listen`. `accept` и закрытие другого конца
  сохранённые данные не меняют.
  При `SO_PASSCRED` получатель получает
  `SCM_CREDENTIALS`. Если опция была включена хотя бы на одном конце
  при отправке, ядро передаёт PID, UID и GID отправителя. Для пакета,
  поставленного в очередь до включения опции, возвращаются 0, 65534 и 65534.
  Один пакет занимает не больше одной физической страницы вместе
  со служебными данными. На сторону можно поставить до 32 пакетов.
  `shutdown` закрывает одно или оба направления пары. Принятые пакеты
  доступны до EOF, а запись в закрытое направление возвращает `EPIPE`.
  Блокирующий вызов ждёт сообщения или места в очереди. `O_NONBLOCK` и
  `MSG_DONTWAIT` возвращают `EAGAIN`, пока другую сторону нужно ждать.
  `pipe` и `pipe2` выдают дескрипторы для чтения и записи байтов в порядке
  поступления. Буфер вмещает 4096 байт, записи до этого размера атомарны.
  Блокирующий вызов ждёт, пока другой процесс прочитает или запишет данные
  либо закроет свой конец. `pipe2` поддерживает `O_CLOEXEC` и `O_NONBLOCK`.
  После закрытия последнего пишущего конца читатель может дочитать буфер
  до EOF. Запись без читателей возвращает `EPIPE`, доставка `SIGPIPE` пока
  отсутствует.
  `eventfd` и `eventfd2` создают 64-битный счётчик, общий для копий
  дескриптора. Запись прибавляет значение, чтение забирает весь счётчик,
  а с `EFD_SEMAPHORE` — единицу. Пустой счётчик ждёт записи,
  переполнение ждёт чтения, а `EFD_NONBLOCK` возвращает `EAGAIN`.
  `poll` ждёт готовности каналов, Unix-сокетов и `eventfd` либо истечения
  таймаута.
  `epoll_create` и `epoll_create1` создают экземпляр `epoll`.
  `epoll_ctl` регистрирует номер дескриптора и открытый файловый объект.
  При закрытии последней ссылки регистрации исчезают. `epoll_wait`
  возвращает готовые события с исходным 64-битным значением `data`,
  поддерживает `EPOLLONESHOT` и ожидание с таймаутом. Наблюдать можно
  каналы, Unix-сокеты и `eventfd`. Вложенные экземпляры, `EPOLLET`
  и `EPOLLEXCLUSIVE` пока не поддерживаются.
  `ppoll` использует те же события и относительный `timespec`. Системный
  вызов возвращает остаток времени и на время ожидания подставляет маску
  сигналов потока. Доставка сигналов пользовательским обработчикам пока
  отсутствует, поэтому такой сигнал ещё не прерывает ожидание.
  Обычные файлы всегда готовы к чтению и записи, вывод в serial готов к записи.
  При каждом сканировании номера разрешаются через текущую таблицу
  дескрипторов процесса. В массиве до 256 элементов обновляется только
  `revents`. У процесса до 256 дескрипторов, а общий пул открытых
  файловых объектов вмещает 512 записей. Исчерпание слотов процесса
  возвращает `EMFILE`, общего пула — `ENFILE`.
  Если нет готовых задач, ближайший таймаут проверяется по TSC
  до появления таймерных прерываний в этом режиме.
  `/dev/null` доступен как символьное устройство `1:3`. Чтение возвращает
  EOF, запись принимает байты без обращения к буферу. Открытый дескриптор
  наследуется как обычный файл, с учётом `O_CLOEXEC`.
  Начальные дескрипторы 0–2 используют общую файловую таблицу. Ввод
  по умолчанию идёт из `/dev/null`, вывод — в serial. `dup`, `dup2`,
  `dup3` и команды дублирования `fcntl` разделяют открытый файл,
  сохраняя `FD_CLOEXEC` отдельно для каждого номера. Это позволяет
  перенаправлять стандартный ввод и вывод через `fork` и `execve`.
  Корень и каталоги файлов Live-образа доступны для обхода. `mkdir` и
  `mkdirat` создают каталоги в общей временной области `/tmp`, учитывая
  режим доступа и `umask`. Открытый каталог можно передать как `dirfd`
  в `openat`, `newfstatat` и `mkdirat`. Временные каталоги живут до
  перезапуска ядра. `getdents64` перечисляет непосредственные имена
  Live-образа и временные узлы. Синтезированный подкаталог появляется
  один раз, даже если в образе у него несколько файлов. Дубликаты
  дескриптора делят позицию, которую можно восстановить через `lseek`.
  В `/tmp` можно создавать обычные файлы через `open` и `openat` с `O_CREAT`.
  Данные хранятся в памяти до перезапуска. Открытые дескрипторы и общие
  отображения сохраняют доступ к данным после `unlink`. Изменение размера
  через `ftruncate` при активном общем отображении возвращает `EBUSY`.
  `fsync` и `fdatasync` завершаются успешно для файлов в памяти и временных
  каталогов. Данные и метаданные уже находятся в памяти к моменту вызова.
  `flock` поддерживает общие и исключительные блокировки файлов в памяти.
  Блокировка принадлежит открытому описанию файла, сохраняется через `dup`
  и `fork` и освобождается при закрытии последней ссылки на это описание.
  `mmap` удерживает страницы, а время жизни открытого описания пока не продлевает.
  `fcntl(F_SETLK)` и `F_GETLK` поддерживают неблокирующие POSIX-блокировки
  диапазонов файлов в памяти, в том числе за концом файла. Владелец такой
  блокировки — процесс. Закрытие любого его дескриптора этого файла
  снимает блокировки процесса на этом файле.
  `rename` и `renameat` атомарно перемещают временные файлы между каталогами
  и заменяют существующее имя. Открытые дескрипторы сохраняют прежние данные
  и inode, даже если имя файла заменено. Переименование каталогов пока не реализовано.
  Доступная клавиатура PS/2 появляется как `/dev/input/event0`. Linux ABI
  передаёт физические коды, нажатия и отпускания через `EV_KEY` и `SYN_REPORT`.
  Поддерживаются блокирующее и неблокирующее чтение, `poll` и `epoll`.
  Независимые открытия имеют отдельные позиции. `EVIOCGKEY` возвращает снимок
  состояния и начинает чтение с новых событий для этого открытия.
  Доступная мышь PS/2 появляется как `/dev/input/event1`. Она передаёт
  относительное движение и состояния трёх кнопок. Снимок кнопок через
  `EVIOCGKEY` сохраняет непрочитанные перемещения. Колесо доступно, если мышь
  ответила идентификатором IntelliMouse. У мыши и клавиатуры отдельные очереди
  событий и общий опрос контроллера без аппаратных прерываний. Тест QEMU
  отправляет движение, кнопки, колесо и клавиши через QMP.
  `symlink` и `symlinkat` создают символические ссылки в доступной для
  записи части `/tmp`. Относительная цель разрешается от каталога ссылки,
  абсолютная — от корня. `readlink` возвращает записанную строку, а `unlink`
  удаляет ссылку и освобождает её место во временной области.
  `MAP_FIXED` заменяет страницы в отдельной области mmap, где нельзя затереть
  основной ELF, интерпретатор или стек. Целые страницы после EOF заняты, но
  недоступны. Обращение к ним пока даёт диагностический #PF.
  `mprotect` меняет права пользовательских страниц ELF, стека и mmap.
  `PROT_NONE` сохраняет данные, а RELRO остаётся читаемым и защищённым от записи.
  Проба проверяет переходы прав без одновременной записи и исполнения.
  Анонимный `mmap(PROT_NONE)` резервирует виртуальный диапазон без выделения
  физических страниц. Когда `mprotect` открывает доступ к части резерва,
  ядро подготавливает таблицы и выделяет нулевую страницу при первом
  обращении. `munmap` освобождает отображения и части резерва.
  `madvise(MADV_DONTNEED)` отбрасывает данные частного анонимного `mmap`,
  сохраняя виртуальный диапазон и его права. Следующее обращение выделяет
  нулевую страницу. Файловые отображения пока возвращают `ENOSYS`.
  `MAP_STACK` принимается как подсказка Linux x86-64. Она сохраняет
  обычные права и размер отображения.
  На одном CPU Linux ABI поддерживает `arch_prctl(ARCH_SET_FS/ARCH_GET_FS)`
  для TLS. Тот же ELF проверяет чтение и запись через FS после возврата из
  `SYSCALL` и проверку пользовательского буфера на границе страниц.
  `fork` и эквивалентный `clone` создают отдельное адресное пространство.
  Общие страницы memfd остаются видны обоим процессам. Приватные страницы
  разделяются только пока они доступны для чтения, а перед записью получают
  отдельную физическую страницу. Таблицы дескрипторов независимы, смещение
  унаследованного открытого файла общее.
  Процессы переключаются на границе системных вызовов с
  сохранением регистров, TLS и состояния FPU/SIMD. `wait4` получает код
  завершения. Типичные пользовательские исключения с действием по умолчанию
  завершают дочерний процесс. При `SIG_IGN` или `SA_NOCLDWAIT` для
  `SIGCHLD` ребёнок освобождается автоматически. Пользовательские обработчики
  `SIGCHLD` пока не вызываются.
  `vfork` и `clone(CLONE_VM|CLONE_VFORK|SIGCHLD)` делят адресное
  пространство и состояние `mmap`, сохраняя раздельные таблицы
  дескрипторов. Родитель ждёт завершения ребёнка. `waitid` с `WEXITED`
  позволяет забрать статус и освободить завершившегося ребёнка.
  `clone` с флагами glibc для `pthread_create` создаёт поток с
  отдельными TID, стеком, FS и маской сигналов. Потоки разделяют PID,
  память, дескрипторы и обработчики сигналов. `exit` завершает текущий
  поток, `exit_group` завершает процесс. После выхода потока ядро
  обнуляет слово `CLONE_CHILD_CLEARTID` и будит ожидающего в том же
  адресном пространстве. `clone3` возвращает `ENOSYS`, и glibc переходит
  на `clone`. Замена образа через `execve` доступна при одном потоке.
  Планировщик хранит до 256 задач, включая начальную. Буферы FXSAVE и XSAVE
  выделяются по размеру состояния CPU для живых задач и освобождаются
  при их завершении. Таблица процессов вмещает до 64 записей с учётом
  завершившихся процессов, чей статус ещё не забрал родитель.
  На пределе `clone` возвращает `EAGAIN`. Таблицы процессов и адресных
  пространств выделяются через PMM. Линковщик проверяет, что ядро
  не занимает область ELF от `0x400000`.
  Проверка `fork` трижды удерживает 24 живых потомка одновременно
  и сверяет все статусы завершения после освобождения барьера.
  `execve` загружает x86-64 ELF и его `PT_INTERP` из Live-образа,
  формирует новый стек с `argv`, `envp` и `AT_EXECFN`. Начальный стек
  Linux ELF и стек после `execve` содержат `AT_SECURE=0`, поскольку
  загрузка сохраняет UID и GID и не даёт полномочий из метаданных файла.
  Относительные пути отсчитываются от корня Live-образа, начальные `./` допускаются.
  Стек начального Linux ELF и нового образа после `execve` может расти
  до 8 МиБ. Ядро выделяет нулевые страницы по мере обращения, сохраняет
  права `mprotect` и оставляет постоянную защитную страницу под стеком.
  Пределы для `argv` и `envp` вместе — 256 указателей и 32 КиБ строк.
  При успешной замене образа PID сохраняется, закрываются дескрипторы
  `FD_CLOEXEC`, обновляется `/proc/self/exe` и просыпается родитель
  `vfork`. Ошибка оставляет прежний образ и дескрипторы доступными.
  В формате Live-образа `MYOSLX66` данные основного ELF и дополнительных
  файлов начинаются на границах 4 КиБ. Полные страницы незаписываемых
  ELF-сегментов отображаются прямо из зарезервированного образа. При добавлении
  права записи `mprotect` выделяет частную копию. Старый формат `MYOSLX65`
  загружает ELF копированием страниц.
  `prctl(PR_SET_NO_NEW_PRIVS, 1)` необратимо выставляет флаг текущего
  потока. `PR_GET_NO_NEW_PRIVS` читает его. Новые процессы и потоки
  наследуют флаг, а `execve` сохраняет его. Загрузчик сбрасывает Linux
  capabilities при смене образа.
  `uname` возвращает шесть полей Linux x86-64, имя MyOS, версию сборки
  и архитектуру `x86_64`.
  `getresuid` и `getresgid` записывают реальный, эффективный и сохранённый
  идентификаторы 32-битными значениями. Тестовый процесс использует
  те же UID и GID, что и в `getuid` и `getgid`.
  `clone(CLONE_NEWUSER | SIGCHLD)` и `unshare(CLONE_NEWUSER)` создают
  пользовательское пространство. До записи `uid_map` и `gid_map`
  идентификаторы без отображения видны как 65534. Одна запись на карту
  отображает только собственный идентификатор в родительском пространстве.
  Для карты GID требуется `setgroups=deny`. `capget` и `capset` читают
  и ограничивают права текущего потока в его пространстве. Дескрипторы
  карт удерживают пространство, к которому относились при открытии.
  `/proc/self/ns/user` ссылается на текущее пользовательское пространство.
  `clone(CLONE_NEWPID)` создаёт вложенное пространство идентификаторов.
  Его первый процесс получает PID 1, усыновляет сирот и при выходе
  завершает своё поддерево. `wait4`, `waitid` и `SCM_CREDENTIALS`
  возвращают идентификаторы в пространстве вызывающего процесса.
  `/proc/self/ns/pid` открывает объект текущего пространства, а открытый
  дескриптор удерживает объект после завершения процесса.
  `CLONE_FS` позволяет процессам делить корень, текущий каталог и `umask`.
  `chroot` меняет корень при наличии `CAP_SYS_CHROOT`, а `chdir` меняет
  текущий каталог. Абсолютные пути и абсолютные цели ссылок разрешаются от
  этого корня, включая имена Unix-сокетов и интерпретатор ELF. Уже открытые
  каталоги сохраняют свои точки отсчёта для операций с дескриптором.
  Вызов `chroot` сам по себе не переносит текущий каталог и не отзывает
  прежний доступ через открытые дескрипторы. Зигота вызывает `chdir("/")`
  и отдельно проверяет унаследованные дескрипторы.
  Пустой каталог `/proc/self/fdinfo` сохраняется как корень после выхода
  вспомогательного процесса Chrome.
  `getdents64` перечисляет открытые слоты процесса через
  `/proc/self/fd`. Дубликаты дескриптора каталога делят позицию обхода,
  а `fstatat` с переходом по ссылке возвращает тип и метаданные
  фактического объекта. Каталог привязан к процессу, открывшему его.
  Для относительных запросов из другого процесса проверяется совпадение
  пользовательского пространства. После выхода владельца каталог
  перестаёт перечисляться и не привязывается к новому процессу.
  `readlink` показывает его inode в виде `user:[номер]`. Открытый
  дескриптор сохраняет ссылку на тот же объект и после `unshare`.
  `AT_RANDOM` указывает на 16 байтов с `RDRAND` на начальном стеке.
  Если процессор не поддерживает инструкцию или не выдаёт данные за
  ограниченное число попыток, тестовый запуск Linux ELF прекращается.
  Linux `getrandom` читает из того же источника. При отказе источника
  возвращаются уже записанные байты либо `EAGAIN` с `GRND_NONBLOCK`
  и `EIO` без этого флага.
  Linux `/dev/urandom` выдаёт байты из того же источника через `read`
  и `pread64`. Смещение игнорируется. `O_NONBLOCK` сохраняется в
  дескрипторе, а отказ источника при чтении до первого байта даёт `EIO`.
  Запись в устройство возвращает `ENOSYS`: отдельного пула энтропии нет.
  `getrlimit` и `prlimit64` читают `RLIMIT_DATA`, `RLIMIT_NOFILE` и `RLIMIT_NPROC`
  для текущего процесса. Через `prlimit64` можно менять мягкий
  `RLIMIT_DATA` в пределах жёсткого и снижать жёсткий лимит. Мягкий
  лимит ограничивает рост приватных записываемых виртуальных отображений,
  включая записываемые сегменты ELF. Основной стек и совместные
  отображения в лимит не входят, а `MADV_DONTNEED` сохраняет учёт
  отброшенных страниц. Лимит наследуется при `fork` и сохраняется через
  `execve`. Если записываемые сегменты нового образа превышают предел,
  `execve` возвращает `ENOMEM` и сохраняет прежний образ.
  `RLIMIT_NOFILE` и `RLIMIT_NPROC` доступны для чтения и отражают
  вместимость таблицы дескрипторов процесса и общей таблицы задач.
  Linux `sysinfo` возвращает время работы в секундах, число потоков и
  размеры памяти в байтах. Общий объём учитывает страницы под управлением
  аллокатора после начальных резервирований. Свободный объём меняется при
  выдаче и при освобождении последней ссылки на страницу. Неподдерживаемые
  показатели, включая подкачку и среднюю нагрузку, имеют значение 0.
  Linux `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` считает время выполнения
  текущего потока. При ожидании готовой задачи планировщик приостанавливает
  учёт. Новый поток начинает с нуля, а `execve` сохраняет накопленное время.
  `CLOCK_MONOTONIC`, `CLOCK_MONOTONIC_RAW` и `CLOCK_BOOTTIME` используют
  TSC с частотой из CPUID либо после калибровки по каналу 2 PIT. Отсчёт
  начинается при запуске Linux ABI на одном CPU с неизменной частотой TSC.
  Системный сон и корректировка хода монотонных часов пока отсутствуют.
  `CLOCK_MONOTONIC_COARSE` округляет ту же шкалу вниз до целой миллисекунды.
  Пробы проверяют ход времени при ожидании, неубывание результата и запись
  `timespec` на границе двух страниц.
  `clock_gettime(CLOCK_REALTIME)` и `gettimeofday` считают время UTC от
  начального показания CMOS RTC, используя тот же TSC. При недоступном
  или некорректном показании RTC запрос календарного времени возвращает
  `EIO`. Проба QEMU сверяет оба вызова с заданной високосной датой после 2038 года.
  `FUTEX_WAIT` и `FUTEX_WAIT_BITSET` ставят поток в ожидание при совпадении
  значения слова. Таймаут `FUTEX_WAIT` задаётся интервалом по монотонным
  часам, а для `FUTEX_WAIT_BITSET` — абсолютным сроком по монотонным
  часам или UTC с `FUTEX_CLOCK_REALTIME`. Планировщик проверяет сроки
  при выборе потока и продолжает проверять их, если готовых потоков нет.
  `FUTEX_WAKE` и `FUTEX_WAKE_BITSET`
  возвращают число разбуженных потоков. Ключ включает адресное пространство,
  виртуальный адрес и признак `FUTEX_PRIVATE_FLAG`. Пробуждение через другое
  отображение той же общей страницы пока отсутствует.
  `rt_sigaction` сохраняет и возвращает настройки сигналов тестового процесса.
  `rt_sigprocmask` меняет маску текущего потока и может вернуть её прежнее
  значение. `SIGKILL` и `SIGSTOP` остаются неблокируемыми.
  Доставка сигнала пользовательскому обработчику требует отдельного
  сигнального кадра и поддержки `rt_sigreturn`.
  Live-образ задаёт абсолютный путь основного ELF. `readlink("/proc/self/exe")`
  возвращает путь текущего образа без завершающего NUL. Повторный запуск
  через `/proc/self/exe` сохраняет этот путь. `AT_EXECFN` содержит имя,
  переданное при запуске, и хранится отдельно от `argv[0]`.
  Вход через `SYSCALL` используется для одного тестового процесса на одном CPU
  под OVMF. Для обычной работы на оборудовании нужен отдельный стек NMI
  на момент переключения со стека пользователя и состояние входа на каждом CPU.
- `make uefi-smoke` — OVMF, NVMe-корень, GOP, ACPI/SMP, запись файла и две
  загрузки с новым NVRAM-образом при каждом запуске.
- `make uefi-installer-smoke` — UEFI Live USB, отмена без изменения диска,
  установка на NVMe, проверка бинарной копии, паролей/прав/времени/ссылок,
  затем две UEFI-загрузки с NVMe без флешки.
- `make installer-test` — сбои записи/flush и аварийные обрывы до активации ESP.
- `make nvme-boot-smoke` — регрессия BIOS, SATA/NVMe, namespaces и четыре CPU.
- `make kernel-x64-nvme-smoke` — два запуска x86-64 Live с одним временным
  NVMe-диском данных. Проверяет выбор отдельного namespace, границы LBA,
  запись с flush, чтение после перезагрузки и неизменность загрузочного диска.
- `make kernel-x64-myfs-smoke` — два запуска x86-64 с одним подготовленным
  MyFS v5 на отдельном NVMe. Проверяет запись, замену файла через rename,
  откат транзакции и чтение сохранённых данных после перезапуска.
  При отказе записи заголовка журнала тест проверяет ответ ошибки и сохранность
  файла при следующей загрузке.

Драйвер x86-64 использует общие очереди NVMe и поддерживает namespace с
512-байтовыми секторами без метаданных. Live-вызов драйвера исключает
носитель загрузки по его MBR ID. Для явно выбранного диска доступны общий
блочный кэш и MyFS с существующим журналом.

Linux ABI подключает MyFS v5 в `/profile`, если Live-корень содержит
`/myos/myfs-volume` с 16 байтами идентификатора. Последний сектор отдельного
NVMe-диска за пределами файловой системы должен начинаться с восьми байт
`MYOSPROF` и того же идентификатора. Монтируется только единственный
совпавший том, уже подготовленный утилитой MyFS.

`make kernel-x64-linux-myfs-smoke` проверяет чтение, запись, права, ссылки,
`openat` после переименования каталога и чтение сохранённого состояния
после повторной загрузки. Тот же тест проверяет POSIX-блокировки диапазонов
через `fcntl(F_SETLK)` и `F_GETLK`, а также `flock` на MyFS. POSIX-блокировка
принадлежит процессу и снимается при закрытии любого его дескриптора данного
inode. `flock` живёт до закрытия последней ссылки на открытое описание файла.

MyFS поддерживает `MAP_SHARED` на чтение и частные файловые отображения.
Запись через дескриптор обновляет общие страницы. Общее отображение удерживает
inode после закрытия файла и переименования. Пока оно существует, усечение
возвращает `EBUSY`. Размер отображения ограничен округлённым до страницы
размером файла. Эти случаи проверяет `make kernel-x64-linux-myfs-smoke`.

Штатная команда запуска Chrome подключает постоянный том при заданном
`CHROME_PROFILE` и открывает профиль из `/profile/chrome`.

OVMF по умолчанию может назначать 64-битные PCI BAR выше 4 ГиБ. Тесты задают
`-fw_cfg name=opt/ovmf/X-PciMmio64Mb,string=0`, чтобы размещение соответствовало
возможностям ядра. Физические накопители тесты не открывают; реальное
оборудование этими проверками не охвачено.
